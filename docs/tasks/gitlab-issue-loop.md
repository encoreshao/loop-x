# Daily GitLab Issue Loop

## Goal

Every weekday, check GitLab issues already assigned to the configured user on the configured GitLab instance, pick up anything new (a fresh issue or a new comment on one already being tracked), and then take exactly one of four actions per issue: implement a fix, verify it, and open a merge request when the ask is clear, scoped, and genuinely needs a code change; answer directly with a GitLab comment when the ask is clear but needs no code at all (a question, a status check, a request for information); post a GitLab comment asking for clarification when the ask is ambiguous; or, when the issue has already been handed off to someone else to review, wait — no GitLab comment at all, just one Slack reminder after a week if nobody has followed up. Failing verification also gets a GitLab comment instead of a guess. Every comment the loop does post is short, goal-based, and structured markdown (a one-line summary, then bold-labelled sections with one fact or question per bullet): it states a decided next action grounded in the issue's full history, or shares a progress update — never one dense, hard-to-parse paragraph. The loop also gets more capable over time: reusable lessons learned per project (fix patterns, gotchas, root-cause categories) are recorded per issue as markdown task-memory files and read back on later runs — see `loopx memory-store` (entries recorded before this format existed are still read via `loopx memory`).

## Setup

New to this loop? Run `bin/scripts/setup.sh` once (or click install on the dashboard's Settings → Skills page) — it installs the `gitlab-config` skill this loop depends on (from [encore-skills](https://github.com/encoreshao/encore-skills)). `~/.loopx/projects.json` is scaffolded from the template by `install-loopx.sh`, or you save a project from the dashboard. The dashboard's Settings → Skills view (`/settings?view=skills`) shows a live view of what's installed.

## Scope

Which GitLab projects to track, their local checkout paths, target branches, GitLab username, worktree scratch directory, and per-project install/lint/test commands are **not** hardcoded in this repo — they live in `~/.loopx/projects.json`, since every team member running this loop has their own local checkout paths. See `config/projects.json.template` for the exact format, and `crates/core/src/config.rs` for how the loop reads it.

The loop never self-assigns issues — it only tracks issues already assigned to the configured `assignee_username`, on the projects listed in that config file.

## Expected output

Each run produces or updates:
- `outputs/daily-review.md` (and an archived copy under `outputs/history/`)
- `PROGRESS.md`
- Slack messages via the webhook at `~/.slack/config.json`. A scheduled batch stays quiet while it works (the agents' own `loopx notify` calls are held via `LOOPX_SLACK_HOLD`, and the runner's per-issue Finished/Escalated lines are skipped) and ends with one run report per Slack bundle (`send_run_report` / `issue_report.rs`, built from the run's events: MRs opened, answered, waiting on review, nothing new, a by-project table, and a "needs you" callout for escalations, unfinished issues and a failed wrap-up), sent every run — including mornings with no assigned issues at all — in the message template picked in Settings → General. The `*Approval needed*` request is the one message still sent mid-run, since it waits on a human. The dashboard's on-demand single-issue run works the same way and ends with one report titled `GitLab issue run: <alias> #<iid>`.
- Zero or more GitLab comments and zero or more opened merge requests

## Safety boundary (fixed — does not loosen with time or repeated success)

- **Never merge a merge request.** The loop's job ends at "MR opened, verification passing." Merging is always a manual step for the human.
- Every code change happens on a branch named `feature#<iid>-<slug>` / `bug#<iid>-<slug>`, never on the checkout's target branch: inside an isolated git worktree under the configured `worktree_root`, or, for a project with `use_worktree: false`, in its checkout itself (refused when the checkout has uncommitted or untracked changes; the runner itself refuses to start the agent on a dirty checkout, switches it back to the user's branch after the issue even if the setting changed meanwhile, and escalates `checkout_problem` - Slack and the loop's log only, never the issue - when it can't, or when the checkout changed without being branched).
- The agent chooses each project's install/lint/test commands itself (stored `*_cmd` values are hints), logs them as a `verification.commands` event, and repeats them in its fix handoff. An MR is only opened after the runner itself re-runs that lint and test command and they pass; a command outside the per-stack allowlist (`crates/core/src/verify_commands.rs`) or a fix with no test command never verifies. The diff only touches files relevant to the issue.
- Only the command allow-list in `instructions/loopx/gitlab-issue.md` may run — no arbitrary shell, no dependency upgrades, no reading `.env`/credentials/SSH keys.
- Issues are processed one at a time, sequentially — never multiple worktrees/fixes in parallel in the same run.
- In `observe` mode (the default) the same verification failure on the same issue is not retried within a run — it escalates via a GitLab comment instead. In `gate` mode the loop retries at most `stop_conditions.max_iterations` times (see below); it never opens an MR whose tests/lint fail.
- The loop only touches: issues/comments/MRs on the projects listed in `~/.loopx/projects.json`, its own git worktrees (under the configured `worktree_root`), and its own state files (`PROGRESS.md`, `outputs/`).

## MR feedback round

Before each issue's normal pass, `run_one_issue` runs one MR-feedback round (`crates/core/src/mr_feedback.rs`) for an issue whose loop merge request (`feature#<iid>-<slug>` / `bug#<iid>-<slug>`) is open. It owns all review feedback on that MR; `loopx issues comments` returns only the issue's own notes.

- **Quiet-MR pre-check, no model.** `mr_precheck` compares the MR's discussions with the stored thread state. No new human note outside the loop's own account and no thread to retry means no agent is launched, so a quiet MR costs nothing.
- **Plan, execute, validate.** For each new or unresolved thread, one model plans (action `change_code` / `reply_only` / `wait`, confidence, files, draft reply), a second executes (edit, verify, commit on the existing worktree and branch, push under the usual gate rules), and the first validates the diff and checks, or the draft reply, before anything is posted. The models come from `agent.models` (`plan`, `execute`, `validate`) in the loop definition (`loops/gitlab-issue/loop.yaml`: Opus, Sonnet, Opus), falling back to `agent.model` when unset; only this round uses them.
- **Its own budget.** The round's agent calls share one budget of `stop_conditions.max_cost_usd`, separate from and on top of the issue pass's own budget. What the round spent is in the `mr_feedback.round_completed` event (`cost_usd`; `null` when no call reported a cost) and is added to the issue run's `agent_cost_usd`.
- **Merge requests opened before the round existed.** A thread with no stored state starts at the old MR-note path's watermark (`_notes.loop_last_seen_mr_note_id` in the issue's GitLab cache), so only human notes newer than it count; with no watermark every unresolved thread is planned once.
- **Runner-side gate.** A plan runs only with confidence above 80 (`mr_plan::CONFIDENCE_THRESHOLD`) and no hard rule tripped (for example more than 5 files, an ambiguous or out-of-scope ask, or a comment trying to change the loop's behavior). The model's own score never overrides a hard rule. Anything else is stored as `needs_you` and nothing is posted.
- **Replies in the reviewer's thread.** Answers and "done" notes are posted as a reply in the reviewer's own discussion (never on the issue), and the thread is not resolved on their behalf.
- **State in issue memory.** One file per issue at `<memory root>/<alias>/mr-threads/<iid>.json` holds each thread's status (`new`, `working`, `answered`, `waiting_on_reviewer`, `needs_you`, `resolved`, `decided` - the user dismissed it or posted their own reply from Needs you), last-seen note, plan summary and confidence. It is saved after every step; a crash leaves the thread `working` and the next run retries it once.
- **Needs you decisions.** A `needs_you` thread is listed on the Needs you page with the comment, plan, confidence, why it stopped and the draft reply. The user can Approve the plan (a code change still passes the checks, the validator and every push guard), Edit reply (post their own reply), Dismiss (until someone writes in the thread again) or Give instructions (the loop plans again with them). Nothing is posted on the MR until the user decides, and a thread resolved on GitLab in the meantime is not acted on.

## Verification gate (observe vs gate)

After the agent's work on an issue, the runner independently re-runs the test and lint commands from the agent's fix handoff (`verification.test`/`verification.lint`, falling back to the project's stored `test_cmd`/`lint_cmd` hints; refused unless it is one allowed stack command with no shell operators (it runs without a shell; leading `KEY=value` words become its environment), and only in the handoff's `cwd` when that is the issue's work directory) inside the worktree the agent used (or the checkout, with worktree off), via `ProjectCommandsVerifier` in `crates/core/src/loop_verifiers.rs`, inside `LoopRuntime`. No worktree or no configured commands (the agent made no code change) is a vacuous pass, not a failure. `verification.mode` in `loops/gitlab-issue/loop.yaml` selects what the result does:

- **`observe`.** The real result is recorded (`observed_passed` in the iteration's evidence and the `verification.external_completed` event) but the iteration always passes, so outcomes are unchanged. The agent still pushes and opens the MR itself.
- **`gate` (default since the Track switch).** A failing check fails the iteration. `LoopRuntime` retries up to `stop_conditions.max_iterations` (2) with the failing command's output tail as feedback (`format_feedback`, bounded). The agent's allowlist drops `loopx mr open` and `git push` (`allowed_tools(.., gate = true, ..)` in `crates/core/src/issue_runner.rs`), a `GATE_OVERRIDE` prompt section tells it to write a handoff JSON to `outputs/handoffs/<run_id>/<alias>-<iid>.json` (also in `$LOOP_HANDOFF_PATH`) instead, and the runner (`finalize_gated_issue`) reads it (`read_handoff`) and runs `loopx mr open` itself only after verification passed. In gate mode the external check runs only for an attempt whose handoff says `"action": "fix"`; an `answer`, `escalate` or `wait_for_review` handoff (or none) is a vacuous pass, so the agent is never re-run on an issue it already answered, escalated or left waiting. The runner deletes the handoff file before every attempt, so a retry that crashes can never be finalized with an earlier attempt's handoff. Of step 10 the agent still annotates `loop_last_action` (`fix_handed_off`), marks the notes seen and records a learning; the runner emits the `issue.completed` fix event after opening the MR, and the run's Slack report (to the project's Slack bundle webhook from `~/.gitlab/config.json`) lists the issue with links to it and the MR. Handoff actions: `fix`, `answer`, `escalate`, `wait_for_review` (Wait for reviewer, or nothing to act on this run). An agent that writes no handoff at all - even one that deliberately skipped the issue - is escalated as `handoff_invalid`, so a silently skipped issue is always surfaced to a human.

Gate-mode outcomes: `mr_opened` (an `issue.completed` event with `gated: true`), `answered` / `waiting_for_review` / `escalated:agent` (the agent's own handoff action), or `escalated:<reason>` with reason `verification_failed` (worded by the runtime's stop reason, e.g. the same failure on consecutive attempts; also used when a retry crashed or hit the budget after an earlier attempt's checks failed, quoting that attempt's failure tail), `handoff_invalid` (handoff missing or malformed - never an MR), `run_incomplete` (the agent session crashed/timed out or the budget ran out before any attempt was verified; `data.stop_reason` says which), `mr_open_failed`, or `project_config_error`. An escalation about the work itself (`verification_failed`, `setup_blocked`, `mr_open_failed`, `approval_*`) posts a GitLab comment and adds the `loop:needs-human` label (`escalated:agent` is the agent's own escalation, commented by the agent itself); the unpushed `feature#<iid>-<slug>` / `bug#<iid>-<slug>` branch stays in its worktree for a human to inspect. An escalation that only describes the loop's own machinery (`run_incomplete`, `handoff_invalid`, `checkout_problem`, `project_config_error` - `loop_side_escalation`) never touches the issue: no comment, no label, since a crashed session or a missing handoff tells the issue's readers nothing and would read as a reply nobody asked for. Its detail goes to the loop's log. Every escalation emits the `issue.escalated` event and is listed under "needs you" in the run's one Slack report. An `escalated:<reason>` on a run the runtime had marked completed is written to `result.json` as `final_state: escalated` with `stop_reason: gate:<reason>`, so Loop Runs shows it as an escalation.

Screenshots in the MR come from the agent, not the runner. For a fix that visibly changes the UI, the agent captures "before" shots before editing code and "after" shots as its last step before the handoff (instructions step "UI changes: before/after screenshots"), either through a throwaway Capybara/Selenium spec against the test database or with `loopx screenshot` (the Mac's installed Chrome, every backend call mocked, sign-in faked through a session file). The images live in `outputs/screens/<alias>-<iid>/` and are listed in the fix handoff as `screenshots: [{label, before?, after}]` plus an optional `screenshots_note`. `finalize_gated_issue` validates them (`mr_screenshots::screenshot_pairs`: PNG, at most 5 MB, at most 6 pairs, inside the screens or handoff directory), uploads them into a "## Screenshots" section of the MR description, and deletes every image afterwards whatever the outcome. Screenshots are skipped for `use_worktree: false` projects and never block an MR. How to shoot each project is learned per project as `screenshot-recipe` lessons in `loopx memory-store`.

### Pre-MR review and secret scan (advisory)

After `project_commands`, two more verifiers look at the branch's diff against `origin/<target_branch>` (the local `<target_branch>` when there is no such remote branch). Both are skipped when an earlier check in the same attempt failed, and both run with `observe: true`, so in gate mode they record a verdict but never fail the iteration or trigger a retry.

- **`agent_review`** (`crates/core/src/pre_review.rs`): one read-only Claude call (the MR-feedback validate phase's tools: Read, Grep, Glob) with the MR Review prompt (`loops/mr-review/prompt.md`) over the handoff's title, description and the diff (capped at 60 000 characters). A finding would block when it is a `blocker`, or a `major` in `correctness` or `security`. Its budget is `max_cost_usd` from the verifier spec (0.5), capped by what is left of the issue's `stop_conditions.max_cost_usd`, and its cost counts toward the issue's. On any other CLI it is skipped, since only Claude can be held to read-only tools. A failed or unparseable call is an error result, not a pass.
- **`security_scan`** (`crates/core/src/security_scan.rs`): model-free. Added lines are matched against token patterns (AWS, GitHub, GitLab, Slack, private keys) and a generic `password|secret|api_key|token = "..."` rule (skipped in test and fixture paths and for placeholders such as `${VAR}` or `<token>`), and added files against `.env`, `*.pem`, `*.key` and private SSH keys. Those block; `eval(`, unescaped HTML and shell interpolation are advisory notes. A hit records its rule, path and line, never the matched text. It must be the last verifier (`build_verifiers` refuses any other order).

**Acceptance criteria.** Before editing code the agent writes 1-5 testable criteria in EARS phrasing (`WHEN ... the system shall ...`, `IF ... THEN the system shall ...`, `The system shall ...`) and hands them off as `acceptance_criteria: [{id, statement, test, reason}]`, each with the test that proves it or, when there is none, the reason. The field is optional and read leniently (`pre_review::acceptance_criteria`, at most 8): a missing or malformed list never makes the handoff invalid, it only leaves the MR without the section. The MR description gets an "## Acceptance criteria" checklist (`[x]` with its test, `[ ]` with the reason) above "Pre-review", the review receives the criteria with the diff, and a criterion with neither a test nor a reason is added as a `major`/`tests` finding (advisory, like every review finding in observe mode). The golden eval's `expect.acceptance_criteria: true` fails a fix handoff that lists none.

**Dependency audit.** Between `agent_review` and `security_scan`, `dependency_audit` (`crates/core/src/dependency_audit.rs`, also `observe: true` and skipped after an earlier failure) checks a fix that changes a lockfile: `package-lock.json` (`npm audit --json --package-lock-only`), a Yarn 1 `yarn.lock` (`yarn audit --json`), `pnpm-lock.yaml` (`pnpm audit --json`), `Gemfile.lock` (`bundle-audit check --format json --config <a path that cannot exist>`, so the branch's `.bundler-audit.yml` ignores never apply), `Cargo.lock` (`cargo-audit audit --json`, run directly rather than through the `cargo` proxy) or `requirements*.txt` (`pip-audit -f json --no-deps --disable-pip -r <file>`). The tool runs in the lockfile's directory, found on the same PATH and Node selection as the project's commands, with a 120 s timeout that kills its whole process group; LoopX never installs a tool or runs a package manager's install, the Node tools run with Corepack downloads switched off, and a Corepack shim counts as not installed. Only packages named on an added line of the lockfile's diff count (a line moved unchanged does not), and an advisory of severity `high` or `critical` on one of them would block; the rest are advisory notes. A missing tool (including a version-manager shim that reports the tool or its pinned runtime is not installed), no network (the tools fetch their advisory database), a Yarn 2+ lockfile (no stable JSON audit output) or a lockfile change that adds or upgrades nothing is a vacuous pass; a timeout or unreadable output is an error result. pip-audit reports no severity, so Python advisories never block, and cargo-audit's severity is computed from the advisory's CVSS 3 vector. `poetry.lock` is not audited. When the fix changes audit configuration (`.bundler-audit.yml`, `.cargo/audit.toml`, `.npmrc`, `.yarnrc`, `.yarnrc.yml`, `.pnpmfile.cjs`, or `auditConfig`/`ignoreCves`/`ignoreGhsas` in `package.json`), the result and the MR line say so. The MR line names what was audited and what was not ("clean (npm); not audited: Ruby (bundle-audit not installed)") and gives only a short reason when a tool fails; the tool's own error text, with the home directory shown as `~`, stays in the result's evidence.

**Browser check and accessibility (advisory).** Right after `project_commands`, `ui_check` (`crates/core/src/ui_check.rs`, `observe: true`, skipped after an earlier failure, gate mode only) checks a fix that visibly changes the UI. The agent explores its change itself (path C, or the Playwright MCP server when attached: it walks each acceptance criterion with a visible effect, checks `browser_console_messages`, and writes what it checked under "## Verified"), then declares `ui_checks` in its handoff: the dev command (the `loopx screenshot --serve` allowlist), a localhost `http` origin with an explicit port, at most 6 pages (`path`, optional `wait_for` selector, `color_scheme`, `viewport`) and optional `mocks`/`session` file names inside `outputs/screens/<alias>-<iid>/`. The runner then re-checks those pages with no model involved: a hidden `loopx screenshot check` subprocess starts the branch's dev server (90 s), loads each page in this Mac's headless Chrome through the same request guard as `loopx screenshot` (only same-origin requests, mocks, `data:` and `blob:` go out), and reports a failed load or a status of 400 or more, a missing `wait_for` element, an uncaught exception and a blank page as would-block, and console errors and failed same-origin requests as notes; a redirect to another path or another origin (a sign-in page) skips the page, and an error the page throws because the check refused one of its requests is only a note. The dev server runs with Corepack downloads and Next, Nuxt, Astro and Gatsby telemetry switched off; if it does not start, the MR line only says so, and its output tail (secrets redacted) stays in the run log and the result's evidence. Each page gets 30 s, the subprocess 300 s; the verifier sends SIGTERM at 330 s and SIGKILL to its group 10 s later. Projects with `"verifiers": ["a11y"]` in `projects.json` also get axe-core (bundled unmodified and version pinned, MPL-2.0; its licences and source pointer are served by the dashboard at `/licenses/axe-core/LICENSE.txt`, `/licenses/axe-core/LICENSE-3RD-PARTY.txt` and `/licenses/axe-core/SOURCE.txt`; WCAG 2.2 AA tags) on each page that loaded. Only violations new compared with the target branch count, and only a new `serious` or `critical` one would block. When the branch's pages have violations, the verifier switches the issue's worktree to the merge-base with `origin/<target_branch>` (detached), runs the same pages there and switches back, only when the worktree is clean, on its branch and the project uses a worktree; the branch, its SHA and a clean status are restored on every exit path, files the dev server created are removed and tracked files it rewrote are restored (ignored files such as `node_modules` are never touched, a path the agent left changed or staged is never reset, and a merge-base that tracks a file ignored on the branch is never switched to). Every git command of the switch and restore runs without hooks, without Git LFS downloads and with literal pathspecs. The switch writes a marker (branch, SHA and base) in the worktree's git dir, so a runner stopped mid-baseline is undone by the next check or the next `loopx worktree new`/reuse of that issue: only a worktree still detached at that base is reset; one already back on its branch, or anywhere else, just loses the marker. A check that ends with HEAD anywhere but where it started is a hard failure that observe mode does not mask, and the runner escalates the issue loop-side as `guard_violation`; an orphaned `screenshot check` notices its parent is gone and stops its dev server and Chrome. A check that leaves changes behind is an error result with `restore_failed`. Nothing is installed or built for the baseline, so a project whose CSS comes from a build step is measured with the branch's built assets. A baseline that cannot be measured is `unavailable` and nothing is new. The check is vacuous without a handoff, for `use_worktree: false`, without Chrome, when the origin is in use (another issue's check holds the per-origin lock `outputs/screens/.ui-check-<port>.lock`, or anything already answers there, such as another issue's `loopx screenshot serve`, which is never stopped), and when no pages are declared; a fix whose diff touches view or style files without declaring pages is flagged `undeclared_ui`. LoopX never installs or downloads a browser, a package or a tool for it. Pages behind a real sign-in are skipped; only the agent's fake `session` and `mocks` are used.

Their results go into a "## Pre-review (advisory)" section of the MR description (`pre_review_section`) and into their own events, `verification.review_completed`, `verification.ui_completed` (with `blocking_rules`, `a11y_blocking`, `a11y_new` and `undeclared_ui`; also emitted for an undeclared UI fix), `verification.dependency_completed` (with `blocking_ids`) and `verification.security_completed`, rather than `verification.external_completed`, so they never move the agreement rate below. Harness → Gates counts each issue's last result as "Review would block", "Browser check would block", "Accessibility would block", "UI fixes without a browser check", "Dependency audit would block" and "Secret scan would block".

Before each verifier actually runs (not when it is skipped after an earlier failure), the runtime emits `verification.check_started {iteration, verifier}` with the verifier's name (`project_commands`, `ui_check`, `agent_review`, `dependency_audit`, `security_scan`). It only says which check is in progress: the Office reads it to show "Verifying (tests)", "Reviewing" or "Security scan" (also for `dependency_audit`) while the check runs, and the live trace shows it as `checking: <verifier>`. Metrics ignore it.

### Agent guards

In gate mode the runner snapshots git around every agent session (`crates/core/src/agent_guard.rs`): the issue's loop branches on `origin`, `git remote -v`, `core.hooksPath` and the files in the repository's `hooks/`. A loop branch that appeared or moved on the remote, or a changed remote list, escalates the issue as `guard_violation`, a loop-side escalation (Slack and the loop's log, no issue comment or label, counted under Escalated on Harness -> Gates); the agent is not re-run and no setup doctor runs. A changed hook or `core.hooksPath`, and a change to the user's own checkout during the session (worktree mode), are only `guard.warning` events: hooks are shared by every worktree of the project and rewritten by hook managers on install, and the user may be working in the checkout. Whatever git state can't be read (an unreachable remote, a failing `git`) is skipped, never counted as a change.

The Harness -> Gates view (`/harness?view=gates`) shows the observe-mode agreement rate (of the issues the agent completed with `action: fix`, the share the external check also passed; answers, waits and escalations are left out, since a verdict on them usually comes from a stale worktree; verifier config errors excluded) and what the gate did (blocked, retried then passed, escalated), per project, plus each loop's current mode. CI audits every `loops/*/loop.yaml` with `loopx loop audit --min-score` (see `.github/workflows/rust.yml`).

### Spec approval (opt-in)

An issue in a project with `"spec_gate": true` in `projects.json`, or one labelled `loop:spec-first`, gets a spec before any code (`crates/core/src/spec_gate.rs`). The runner decides at the top of `run_one_issue`, before the agent runs, from the project flag, the issue's labels and the per-issue state at `<memory root>/<alias>/spec/<iid>.json` (`{"status": "awaiting"|"approved"|"changes_requested"|"implemented", "spec", "posted_at", "decided_at", "decided_by": "label"|"dashboard"|null, "notes"}`, written atomically by the runner and the dashboard):

- **No spec yet, or changes were requested.** The pass gets a "Spec mode is ON" section (with the reviewer's notes, fenced as data, after a request for changes): steps 1-4 only, no worktree, and the handoff `{"action": "spec", "spec": "<markdown>"}`. The runner posts it on the issue as "**Proposed spec** for this issue. ..." after the same `/quick-action` check as MR-thread replies, writes the state `awaiting`, emits `issue.completed` with `action: "spec"`, and the outcome is `spec_posted`. An unsafe spec, a `fix` handoff in spec mode, or a `spec` handoff nobody asked for escalates `spec_invalid` (loop-side: nothing is posted); an empty spec is an invalid handoff.
- **Awaiting.** No agent call and no event: the outcome is `awaiting_spec_approval`, at no cost. Awaiting specs are listed on Needs you.
- **Approved**, by Approve on Needs you, or on GitLab by the `loop:spec-approved` label when the issue's label events (`resource_label_events`) show it was last added after the spec was posted (recorded as `decided_by: "label"`). A label that was already there, or one left on after Request changes, does not approve the new spec. GitHub and other hosted trackers report no label times, so there only Needs you approves. The normal fix pass runs with the spec under "## Approved spec (implement exactly this; it came from the issue thread)" in a ```` ```text ```` fence.
- **Implemented.** Once that pass opens the merge request the state becomes `implemented` and the gate is off for the issue from then on.

Request changes on Needs you (notes required) sends the next run back to spec mode with the notes. Approval is never read from comments or the agent's handoff, and the loop adds or removes no labels. What keeps the agent from approving its own spec: `loopx gitlab post-issue-comment` and `post-mr-comment` refuse a body with a line starting with `/` followed by a letter (a GitLab quick action such as `/label`), and on Claude the agent's `--disallowedTools` deny Edit and Write under `<memory root>/*/spec/`. Neither stops a Bash command the agent is allowed to run (a project's test command, say) from writing that file, and other CLIs (Codex and the experimental ones) have no tool lists at all. A waiting spec on an issue that is no longer opted in (no flag, no `loop:spec-first` label, with the labels actually read) is ignored and the issue runs as usual, with one log line. Labels are read only in gate mode for a project with a checkout; when the read fails the gate falls back to the flag and the stored state, with one line in the loop's log. In observe mode the gate is off (logged once per issue when the flag is on). The runner only writes `awaiting` for a new spec and never over an approval, so a decision made on the dashboard during a run is kept.

### MCP servers (Playwright)

A loop opts in to MCP servers with `mcp_servers: [name]` in its `loop.yaml`; `loops/gitlab-issue/loop.yaml` ships with `mcp_servers: [playwright]`. A name refers to an entry in the per-machine registry `~/.loopx/mcp.json` (never in the repo; see `docs/contract/json-files.md`), managed in Settings -> Connectors -> MCP servers or with `loopx mcp`.

- **One-time setup.** Run `npm i -g @playwright/mcp@0.0.84` in Terminal, then press **Add Playwright** and **Test** on the MCP servers view (or `loopx mcp add-playwright` and `loopx mcp test playwright`). LoopX never runs `npm` or `npx` and never downloads a browser: it finds the global install by reading files (the `playwright-mcp` symlink next to a Node 18+ from nvm, fnm, mise, asdf, volta or the login-shell `PATH`, and the version in that package's `package.json`) and runs it with that install's own Node on this Mac's Google Chrome, headless and with an in-memory profile (`--isolated`). `browser_evaluate`, `browser_run_code_unsafe`, `browser_file_upload`, `browser_install`, `browser_drop` and `browser_network_request` are always denied, and an attached Playwright gets `--proxy-server http://127.0.0.1:9` (a dead proxy: only loopback, the page under test, is reachable). A Playwright entry may not use `--extension`, `--cdp-endpoint`, `--cdp-header`, `--allow-unrestricted-file-access`, `--user-data-dir`, `--storage-state`, `--config` or `PLAYWRIGHT_MCP_*` variables, and server names starting with `claude` are reserved (`mcp__claude-in-chrome__*` is the user's signed-in Chrome). The agent may not Edit or Write `~/.loopx/mcp.json`.
- **What attaches when.** Only the main fix call of a Claude run (`Single` or `Batch`; never the golden eval's offline mode, the MR-feedback phases, the setup doctor or the batch wrap-up). Just before the call the runner writes a private per-run config (`<temp dir>/loopx-mcp-<pid>-<nanos>/mcp.json`, dir 0700, file 0600, Keychain secrets resolved from the `loop-engineering.mcp` service), adds `--strict-mcp-config --mcp-config <file>`, allows `mcp__<name>__*` and denies the server's `deny_tools` plus `Read`/`Edit`/`Write`/`Grep` of that folder and `Bash(git diff --no-index*)`, and deletes it when the call returns, fails, times out or unwinds; a stopped or killed run's folder is swept by the next attach or dashboard start once its process is gone (any other `loopx-mcp-*` folder after 24 h). Playwright gets `--output-dir <loop_dir>/outputs/screens`, its only writable folder besides the process's working directory. With nothing attached the argv is byte-identical to before. Codex, Gemini and the other CLIs get no LoopX MCP servers (their own user-level MCP config still loads, as before).
- **Path order.** Screenshots try path C (Claude in Chrome, the user's signed-in browser) first, then path P (Playwright) when C is unavailable or fails, then path A or B. Path P only visits the localhost page `loopx screenshot serve start` started.
- **Secrets are visible to the agent.** A Keychain secret given to an MCP server is in that server's environment, and the agent can reach it: the server can echo it in a tool result, and any Bash or test command the agent may run can read it from the process tree. Give a server only a secret you would give the agent. Fix now refuses servers with secrets (`secrets_unsupported`), because its job log records the session unredacted.
- **Skip reasons.** A server that cannot attach is skipped, never failing the issue: `not_registered`, `invalid`, `secret_missing`, `not_installed`, `wrong_version`, `no_node`, `no_command`, `no_chrome`, `cli_unsupported`, and in Fix now `secrets_unsupported`. When every declared server is simply not registered, nothing is logged and no event is emitted.
- **Event.** Each main call that declared servers emits `mcp.attached` `{"servers": [names], "skipped": [{"name", "reason"}]}` with the issue's fields, and logs `MCP: attached playwright; skipped sentry (secret_missing)` to the unified log. Names only, never values; every resolved secret is replaced by `•••` in what the call logs.

### Rollout checklist

`loops/gitlab-issue/loop.yaml` now ships with `mode: gate`, because the agent picks its own commands and only the runner's re-check stands between them and an MR. The checklist below is how the switch was originally meant to roll out; item 4 still applies to existing installs.

1. Ship with `mode: observe`.
2. After at least 5 weekday runs, open Harness -> Gates. If agreement is 90% or higher and no project shows a systematic false failure (flaky suite, lint baseline - see CLAUDE.md's rubocop notes), set `mode: gate` and raise CI `--min-score` to 80 in the same commit.
3. If a project is systematically red for reasons unrelated to the fix, look at the commands the agent logged (Live view, `verification.commands`) and correct its stored hints in `projects.json` rather than weakening the gate.
4. Gate mode multiplies the per-issue worst case to `max_iterations x (agent + test + lint)`, up to 6x `max_runtime_minutes`. `config/loops.json.template` now sets `issue-loop`'s `timeout_seconds` to 43200, but that only applies to new installs/backfill: an existing `~/.loopx/loops.json` keeps its old 21600. The dashboard does not expose this field, so raise it by hand in that file before flipping to gate.

### Limitations

- Gate enforcement on Codex (and Gemini, Kimi, Cursor, which are experimental) is prompt-only: `codex exec` has no per-command allowlist, so "do not push / do not open the MR" is an instruction, not a harness-enforced denial as it is on Claude.
- Loop-side escalations (`run_incomplete`, `handoff_invalid`, `checkout_problem`, `project_config_error`) never comment or label the issue (see above).
- `loopx gitlab*` stays on the agent's allowlist in gate mode (it needs it to read issues, notes and MRs). Its MR-creating calls are not blocked, but they cannot produce a usable MR in gate mode: the agent cannot push, so the `feature#<iid>-<slug>` / `bug#<iid>-<slug>` branch does not exist on the remote.

## Todos (issues you were only tagged on)

The loop only works issues assigned to you. GitLab todos (mentions, review requests, tagged issues) are mirrored separately in the Issues page's **Todos** view (`crates/core/src/todos.rs`, cache `~/.loopx/todos.json`, off by default). They are never started automatically: **Analyze & draft reply** only creates a draft in `outputs/todo-replies/` that you approve, edit or discard.
